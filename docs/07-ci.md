# 07 CI

The same `tool/build.sh` runs in CI. Do not write a second build path in YAML: two paths drift, and the checks in the script protect only the builds that go through it.

Full workflow: [`template/.github/workflows/release-build.yml`](../template/.github/workflows/release-build.yml).

## Trigger: manual

```yaml
on:
  workflow_dispatch:
    inputs:
      tier:    { type: choice, options: [staging, prod], default: staging }
      target:  { type: choice, options: [appbundle, apk], default: appbundle }
      version_name: { required: false }
```

Release builds start when a person decides, not on every push. Merging code and releasing it are separate decisions, and a push-triggered build takes a version code whether or not anyone ships it.

## One build at a time

```yaml
concurrency:
  group: release-build
  cancel-in-progress: false
```

The ledger is read at the start and written at the end. Two runs in parallel would both read code 57 and both build 58. The concurrency group queues the second run. The `mkdir` lock in the script only protects a single machine.

## Pin the toolchain

```yaml
- uses: subosito/flutter-action@v2
  with:
    flutter-version: "3.44.7"
```

A different Flutter or Java version produces a different binary from the same commit. Pin both, and change them in a commit like any other change.

## Signing from secrets

```yaml
- name: Signing
  env:
    KEYSTORE_B64: ${{ secrets.ANDROID_KEYSTORE_B64 }}
    KEY_PROPERTIES: ${{ secrets.ANDROID_KEY_PROPERTIES }}
  run: |
    echo "$KEYSTORE_B64" | base64 --decode > android/app/release.keystore
    printf '%s\n' "$KEY_PROPERTIES" > android/key.properties
```

Both files must be in `.gitignore`. Otherwise the store-tier clean-tree check in `build.sh` sees them as uncommitted changes and refuses to build.

With Play App Signing, this keystore is the **upload key**. Google re-signs with the app signing key, and a lost upload key can be reset through Play Console. Without Play App Signing, losing this key means you can never update the app again.

## Build

```yaml
- name: Build
  env:
    VERSION_NAME: ${{ inputs.version_name }}
    NOTE: ci run ${{ github.run_id }}
    OUT_DIR: ${{ github.workspace }}/dist
  run: tool/build.sh ${{ inputs.target }} --release --tier ${{ inputs.tier }} --bump
```

- CI always passes `--bump`. A CI build exists to be distributed, and a distributed build needs a new code.
- An empty `VERSION_NAME` keeps the last name, because the script uses `${VERSION_NAME:-$last_name}`.
- `NOTE` links the ledger row to the CI run.

## Record

```yaml
- name: Record
  run: |
    git config user.name "release-bot"
    git config user.email "release-bot@users.noreply.github.com"
    git add tool/versions.tsv pubspec.lock
    git commit -m "build(${{ inputs.tier }}): record release build"
    git pull --rebase
    git push
```

Without this step, the next run reads the same ledger and takes the same code. The ledger is append-only, so `pull --rebase` resolves cleanly unless someone else appended a row at the same time. If the push fails, the job fails. The artifact is still uploaded, but read the ledger before the next build.

Branch protection must allow the bot to push to the branch, or use a deploy key or a GitHub App token with that permission.

## Upload the artifacts and symbols

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: ${{ inputs.tier }}-${{ github.run_id }}
    path: dist/
```

`dist/` contains the artifacts and `dist/symbols/`. CI artifact retention is limited (90 days by default on GitHub). Copy production symbols to permanent storage, or upload them to your crash reporter in an extra step.

## Local and CI together

Both read and write the same ledger. Pull before a local build, and commit and push the ledger after it. If local builds are only for devices and never for stores, use rebuild in place locally (no `--bump`) and let CI own every code that reaches a store.
